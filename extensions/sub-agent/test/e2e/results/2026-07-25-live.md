## 发现汇总

### F-1（低，错误语义优先级）send 在并发槽满时掩盖 BUSY

`manager.send` 先查 `runningSlots` 再查 agent 状态：槽满时向 RUNNING agent send 返回
`SUBAGENT_CONCURRENCY_LIMIT` 而非 `SUBAGENT_BUSY`。行为安全（无副作用、不排队），但错误语义
不精确，重试引导（"等现有 run 结束"）碰巧正确。若希望精确语义，可先解析 agent 再查槽位，
或接受现状并在 README 注明优先级。

### F-2（中，设计缺口）list 的模型可见输出只有计数

`subagent_list` 的 content 仅为 `Listed N ...` / `Found N ...`；items 与 `nextCursor` 只存在于
`details`（模型不可见，仅 UI/程序化消费者可用）。后果：

- 模型无法通过 list 发现 agentId/state/label，只能依赖 spawn/send 文本与错误消息中的 ID；
- 模型永远无法获得 `nextCursor`，分页对 LLM 调用者不可达（L1 无法按设计由模型执行）。

建议：把 items 的紧凑 JSON 摘要与 `nextCursor` 放入 content 文本（list 输出天然是小对象，
远低于 1 MiB 限制），或在 README 明确"list 面向 UI/命令，模型应自行跟踪 ID"。
单元测试（manager.test.ts:538）已覆盖分页逻辑本身。

### F-3（提示）两类输入校验在 live 路径不可达

未知字段与 >64 KiB task 会在模型 API 层被剥离/截断，extension 校验兜底逻辑无法经真实模型
调用触发；已由 contracts 单元测试覆盖。属正常分层防御，无需处理。

### F-4（提示）CANCEL_ALREADY_REQUESTED 窗口极小

协作取消的终态提交非常快，顺序调用几乎总是落在 `RUN_ALREADY_TERMINAL`；同块并行双 cancel
可确定性命中 `CANCEL_ALREADY_REQUESTED`（`pendingCancelRunIds` 同步守卫有效）。
`CANCEL_STALE` 要求 agent 仍有 active run。测试时序已记录在 RUNBOOK。
