# bash-permissions v1 规格

- 状态：已确认，待实现
- extension：`bash-permissions`
- 适用版本：v1
- 最后确认日期：2026-07-19

## 1. 目标

`bash-permissions` 在 LLM 调用 Pi 内置 `bash` 工具时，根据用户维护的正则规则把命令判定为绿色、黄色或红色，并在命令实际执行前采取对应动作。

该 extension 的目标是减少合作型 LLM 因判断失误造成的危险操作，不是 OS 沙箱，也不构成不可绕过的安全边界。

## 2. 范围与非目标

### 2.1 纳入范围

- 只处理 LLM 发起的 Pi 内置 `bash` tool call。
- 使用 Pi 的 `tool_call` 前置事件，在命令执行前完成判定。
- 在 TUI、RPC、JSON 和 print 模式中，只要调用来自 LLM 的内置 `bash` 工具，就应用同一份运行时策略。

### 2.2 不纳入范围

- 用户主动输入的 `!` 或 `!!` 命令。
- RPC 客户端主动发起的直接 bash 执行。
- 其他 extension 自行调用 `pi.exec`、`child_process` 或其他进程 API。
- 恶意模型、提示词注入或刻意规避正则规则的攻击场景。
- OS 级文件系统、进程或网络隔离。
- 独立的 bash 审计日志。
- 项目级配置文件。

## 3. 三色模型

### 3.1 绿色

- 命令未命中任何红色或黄色规则。
- extension 不修改命令、不增加提示，直接交给 Pi 原始 bash 工具执行。
- v1 采用黑名单制度，因此绿色是默认状态。
- 绿色只表示“未命中当前已知风险规则”，不表示命令经过了安全证明。

### 3.2 黄色

- 命令存在一定风险，但在正常开发中可能有合理用途。
- 第一次命中时不执行命令，并向 LLM 返回复审信息。
- 黄色规则分为：
  - `suggest`：给出一个更安全的命令建议。
  - `review`：不给出替代命令，要求 LLM 重新检查必要性和替代方案。
- extension 不自动替换或执行 `suggestedCommand`。
- LLM 完成一次复审后，可以在严格限定的下一轮重新提交原命令并获得一次放行。

### 3.3 红色

- 命令属于通常不应出现在正常编码任务中的灾难性操作。
- 命中后始终拒绝执行。
- 返回信息必须要求 LLM 停止当前方案、反思产生危险命令的原因，并改用安全方案。
- 重试不会产生放行资格。
- 连续命中红色规则不会触发 extension 主动中止整个 Agent；每次调用只会继续被拒绝。

## 4. 文件布局

### 4.1 仓库及 package 内的默认模板

```text
extensions/bash-permissions/
├── package.json
├── README.md
├── defaults/
│   ├── yellow.json
│   └── red.json
├── src/
│   └── index.ts
├── test/
├── tsconfig.json
└── biome.json
```

发布 package 时必须显式包含 `defaults/`。

### 4.2 安装后的用户配置

extension 必须通过 Pi 的 `getAgentDir()` 确定用户配置根目录，不在实现中硬编码 `~/.pi/agent`。在默认 Pi 环境中，实际路径为：

```text
~/.pi/agent/bash-permissions/
├── yellow.json
└── red.json
```

源码模板和用户配置职责不同：

- `defaults/*.json` 是随 package 发布的首次初始化模板。
- 用户目录中的两个 JSON 文件是运行时策略的唯一配置来源。
- 用户不应直接修改已安装 package 内的模板文件。

## 5. 初始化与生命周期

### 5.1 首次初始化

每次 `session_start` 时，extension 必须：

1. 定位用户配置目录。
2. 创建缺失的配置目录。
3. 从 package 的 `defaults/` 中复制缺失的 `yellow.json` 或 `red.json`。
4. 不覆盖任何已经存在的用户文件。
5. 完整读取、严格校验并编译两个文件。
6. 生成当前 session 专用的不可变运行时策略快照。

首次创建文件后，应通知用户实际配置路径。

### 5.2 Session 快照

- 配置只在 `session_start` 时加载。
- 用户在当前 session 中修改配置文件，不得影响已经生成的运行时快照。
- 用户执行 Pi 自带的 `/reload` 后，重新进入 `session_start`，再校验文件并创建新快照。
- 新建、恢复、fork 或切换 session 时，均按 Pi 生命周期重新创建快照。
- v1 不使用文件 watcher，也不注册自定义 reload 命令。

### 5.3 升级行为

- extension 升级不得合并、更新或覆盖已有用户配置。
- 新版默认规则只自动提供给首次初始化的用户。
- 如果未来配置 schema 版本发生变化，旧格式必须明确报错并要求用户主动迁移，不得静默修改。

## 6. 配置格式

### 6.1 通用规则

- 文件格式为严格 JSON，不是 JSONC。
- 顶层 `version` 在 v1 中必须为 `1`。
- 不接受未知字段。
- 所有必填字符串必须是非空字符串。
- 正则按大小写敏感方式编译，不支持用户配置 `flags`。
- 用户配置被视为可信本机输入，但无效 JSON、schema 或正则会导致当前 session 禁用 extension。
- 实现应为配置文件大小、规则数量和单条正则长度设置合理上限；超过上限视为配置无效。
- 不得截断 bash 命令后再做匹配。

### 6.2 `yellow.json`

```json
{
  "version": 1,
  "rules": [
    {
      "name": "Git 强制推送",
      "pattern": "\\bgit\\s+push\\b.*--force\\b",
      "type": "suggest",
      "message": "强制推送可能覆盖远端历史，请优先采用更安全的方式。",
      "suggestedCommand": "git push --force-with-lease"
    },
    {
      "name": "发布 npm 包",
      "pattern": "\\bnpm\\s+publish\\b",
      "type": "review",
      "message": "发布会改变外部状态，请重新检查是否确有必要以及发布目标是否正确。"
    }
  ]
}
```

黄色规则字段：

| 字段 | 要求 |
| --- | --- |
| `name` | 必填；用于向用户和 LLM 标识命中的规则 |
| `pattern` | 必填；JavaScript 正则表达式源码 |
| `type` | 必填；只能为 `suggest` 或 `review` |
| `message` | 必填；用户配置的规则特有风险说明 |
| `suggestedCommand` | `suggest` 必填，`review` 禁止出现；只作为纯文本返回 |

`suggestedCommand` 不支持 `$1`、`$2` 等捕获组展开，也不支持其他模板替换。

### 6.3 `red.json`

```json
{
  "version": 1,
  "rules": [
    {
      "name": "关闭本机系统",
      "pattern": "\\bshutdown\\s+(?:-h\\s+now|now)\\b",
      "message": "该命令会关闭本机系统。请停止当前方案，反思为什么需要执行该操作，并改用不会影响本机可用性的方案。"
    }
  ]
}
```

红色规则字段：

| 字段 | 要求 |
| --- | --- |
| `name` | 必填；用于向用户和 LLM 标识命中的规则 |
| `pattern` | 必填；JavaScript 正则表达式源码 |
| `message` | 必填；用户配置的规则特有拒绝与纠偏说明 |

### 6.4 严格校验

任一文件出现下列情况时，两个文件均不得生成运行时策略：

- JSON 语法错误。
- `version` 不受支持。
- 缺少或增加 schema 未定义的字段。
- 字段类型错误或必填字符串为空。
- 黄色 `type` 非法。
- `suggest` 缺少 `suggestedCommand`。
- `review` 包含 `suggestedCommand`。
- 正则无法编译。
- 配置规模超过实现定义的上限。

错误信息必须指出文件路径、规则序号或名称、字段及具体原因。

## 7. 动态占位符

`pattern` 支持两个运行时占位符：

- `{{cwd}}`：当前 Pi session 的 `ctx.cwd`。
- `{{home}}`：当前用户的主目录。

只允许这两个双花括号占位符。出现其他同类占位符时，配置校验失败，避免拼写错误被当作普通正则文本。

在 `session_start` 编译规则时，extension 必须：

1. 获取两个路径的当前值。
2. 将路径转换为正则字面量，即转义路径中具有正则含义的字符。
3. 替换规则中的所有对应占位符。
4. 再将完整 pattern 编译为正则。

因此占位符会随 session 动态变化，但在同一 session 的运行时快照中保持不变。

默认删除规则还应覆盖 `.`, `./*`, `$PWD`, `${PWD}` 和 `$(pwd)` 等常见文本表达。该机制只匹配 LLM 提交的命令文本，不执行 shell AST 解析，也不解析命令运行后才得到的真实路径。

## 8. 判定算法

对每个 LLM `bash` tool call，按以下顺序执行：

1. 如果当前 session 的 extension 状态为 disabled，直接返回，不干预 Pi 原始行为。
2. 取得 LLM 提交给 bash 工具的完整原始命令，不截断、不重写。
3. 使用全部红色规则匹配命令。
4. 如果命中一条或多条红色规则，阻止命令并返回全部红色命中项。
5. 只有未命中红色时，才使用全部黄色规则匹配命令。
6. 如果未命中黄色规则，命令为绿色，直接执行。
7. 如果命中黄色规则，检查是否存在当前命令可用的单次复审放行资格。
8. 有有效资格时，消费资格并允许命令执行；否则阻止命令、返回全部黄色命中项并创建下一轮复审资格。

同一颜色内不得采用“第一条命中即停止”。红色始终优先，黄色资格永远不能覆盖红色判定。

## 9. 黄色复审状态机

### 9.1 命令同一性

为判断 LLM 是否在复审后重新提交同一命令，只进行以下规范化：

- 将 CRLF 换行转换为 LF。
- 去掉整条命令首尾空白。
- 保留内部空格、换行、引号、参数和 shell 结构原样。

内部内容有任何变化，都视为新命令并重新执行完整红黄判定。

### 9.2 放行条件

- 第一次黄色命中始终阻止执行。
- 放行资格只能在紧接着的下一次 LLM 响应中使用。
- 必须重新提交规范化后完全相同的命令。
- 每份资格只能消费一次。
- 同一条 assistant 消息中重复出现的相同 tool call 不算完成复审，不得提前消费资格。
- 同一轮中出现多个不同黄色命令时，每个规范化命令可拥有独立资格。

### 9.3 失效条件

出现任一情况时，资格立即失效：

- 紧接着的下一次 LLM 响应没有重试该命令。
- 用户发送了新消息。
- 命令内部内容发生变化。
- session 被新建、恢复、切换或 fork。
- extension 或 session 执行 `/reload`。

资格只保存在内存中，不写入 Pi session 或外部文件。

## 10. 返回给 LLM 的协议

extension 使用固定中文协议外壳，并在其中加入用户配置内容。用户不能通过遗漏文字改变核心执行语义。

### 10.1 黄色响应必须包含

- 明确说明原命令没有执行。
- 明确说明判定为黄色。
- 列出全部命中规则的 `name` 和 `message`。
- 对 `suggest` 规则列出纯文本 `suggestedCommand`。
- 要求 LLM 重新检查命令是否必要以及是否存在更安全方案。
- 说明只有紧接着的下一轮原样重试才能获得一次放行。

### 10.2 红色响应必须包含

- 明确说明原命令没有执行且不会被放行。
- 明确说明判定为红色。
- 列出全部命中规则的 `name` 和 `message`。
- 要求 LLM 停止当前危险方案。
- 要求 LLM 反思为什么产生该命令，并及时改用安全方向。

### 10.3 其他约束

- `message` 和 `suggestedCommand` 都作为纯文本处理。
- extension 不自动执行建议命令。
- extension 不向 system prompt 注入权限规则或黑名单内容。
- 反馈只在规则实际命中时通过被阻止的 tool result 返回。

## 11. 默认规则集

默认模板必须提供开箱即用的规则，减少用户首次配置成本。用户随后可以直接增删改两个文件中的任意规则。

### 11.1 默认红色范围

默认红色规则应保持小而保守，只覆盖常见、系统级或整体项目级灾难操作：

- 递归强制删除文件系统根目录或其全部内容。
- 递归强制删除系统关键目录本身或其全部内容。
- 递归强制删除整个用户主目录或其全部内容。
- 递归强制删除当前 session 的 `{{cwd}}` 或其全部内容。
- 格式化、擦除或直接覆写磁盘设备，例如危险形式的 `mkfs`、`wipefs`、`diskutil eraseDisk`，以及把 `dd` 输出指向块设备。
- 对根目录或系统关键目录递归执行破坏性 `chmod`、`chown`。
- 典型 fork bomb。
- 杀死 PID 1 或大范围杀死系统进程。
- 关闭、重启或停止本机系统。

精确正则必须尽量降低误报，并为每种受支持写法提供自动化测试。未落入上述范围的新增默认红色类别，需要重新审视是否违反“红色只用于灾难性操作”的原则。

### 11.2 默认黄色范围

默认黄色规则覆盖有数据损失、提权或外部状态变更风险，但在开发中可能合理使用的常见操作：

- 递归删除项目内子目录或大量文件，但不包括已归入红色的整个 `{{cwd}}`。
- Git 工作区丢弃、清理、历史改写、分支删除和强制推送。
- `sudo`、`su` 等提权执行。
- 终止普通进程或批量终止进程。
- 发布 package、推送制品、部署或改变远端环境。
- 数据库删除、清空或高风险 schema 变更。
- 容器、镜像、volume 或全局缓存的大范围清理。
- 下载内容后直接交给 shell 或解释器执行。

精确正则和默认提示语必须保存在两个默认模板中，并由测试固定其预期匹配与非匹配案例。

### 11.3 默认语言与平台

- 默认规则名称、风险信息、建议和固定协议使用中文。
- v1 默认规则正式面向 macOS 和 Linux 的 Bash 命令。
- extension 在 Windows 上必须能够安全加载，但默认规则不承诺完整覆盖 PowerShell、`cmd.exe`、`diskpart` 等 Windows 命令。

## 12. 启用、停用与可见状态

### 12.1 正常启用

- 不弹出常规通知。
- 使用带 extension 前缀的状态键 `bash-permissions`。
- 状态栏显示当前运行时快照的黄色和红色规则数量，例如 `bash-permissions: 8 yellow / 6 red`。

### 12.2 首次创建配置

- 创建完成后通知一次用户配置文件的实际路径。
- 后续 session 不重复提示，除非又创建了缺失文件。

### 12.3 配置或初始化失败

- 当前 session 将 extension 标记为 disabled。
- 后续 bash tool call 不做任何拦截，恢复 Pi 原始行为。
- TUI/RPC 模式弹出醒目错误，并持续显示 `bash-permissions: disabled`。
- JSON/print 等无 UI 模式通过错误流报告初始化失败，不输出正常状态噪声。
- 错误必须明确说明：extension 没有正常运行，当前 bash 调用不受其保护。

### 12.4 不提供的 UI

- 不注册 `/bash-permissions` 或其他 slash command。
- 不提供配置编辑器、重置按钮或交互式规则管理界面。

## 13. 持久化、隐私与副作用

- 外部持久化仅包含两个用户配置 JSON 文件。
- 不保存独立命令日志、命中统计或审计数据库。
- 当前策略快照和黄色放行资格只存在于内存。
- Pi 自身仍会按原有行为记录 tool call 与 tool result；extension 不复制这些记录。
- extension 不发起网络请求、遥测或后台上传。
- extension 不启动 watcher、长期进程、socket 或 timer。
- 首次创建配置目录和文件是唯一新增的文件系统副作用，必须在 README 中说明路径和清理方式。

## 14. 正则限制

- 使用 Node.js 原生 `RegExp`，不增加 RE2 等运行时依赖。
- 用户维护的全局配置被视为可信输入。
- 原生正则没有执行超时，错误的复杂表达式可能导致灾难性回溯并卡住 Pi。
- 默认规则必须避免已知灾难性回溯结构，并通过长输入测试。
- README 必须提醒用户避免嵌套、重叠量词等高风险写法。
- extension 不截断待检查命令，也不因命令过长生成配置文件之外的隐藏颜色规则。

## 15. 依赖与实现约束

- v1 不新增运行时依赖。
- 使用 Node.js 标准库和 `@earendil-works/pi-coding-agent` API 完成文件初始化、配置读取和 tool call 拦截。
- Pi package 仅作为 `peerDependencies`，版本范围为 `"*"`。
- extension 工厂函数不得读取文件或启动长生命周期资源；初始化在 `session_start` 中完成。
- 外部数据先按 `unknown` 读取并严格校验，不使用 `any` 绕过类型检查。
- 共享运行时状态必须以不可变快照或并发安全方式管理。
- 配置文件创建必须避免覆盖并发写入的用户文件。

## 16. 验收标准

实现至少通过以下自动化场景：

1. 缺少两个用户配置时，从 package 默认模板创建两份文件。
2. 只缺少其中一个文件时，只创建缺失文件，保留已有文件字节不变。
3. extension 升级或多次启动不覆盖已有配置。
4. 有效配置在 `session_start` 生成快照，session 中途修改文件不影响快照。
5. `/reload` 后读取新配置并生成新快照。
6. 无效 JSON、schema、版本、占位符使用或正则使 extension 在当前 session disabled，并给出精确错误。
7. disabled 状态下 bash tool call 完全回到 Pi 原始行为。
8. 绿色命令不被修改或阻止。
9. 红色命令每次都被阻止，且红色优先于黄色和任何黄色放行资格。
10. 同一命令命中的全部红色或黄色规则均出现在返回信息中。
11. 黄色命令第一次被阻止，下一次 LLM 响应中的相同命令只放行一次。
12. 同一 assistant 消息中的重复调用、改变内部内容、用户新消息和 session 生命周期变化都会阻止或清除错误使用的放行资格。
13. `suggestedCommand` 只作为纯文本返回，不被执行或进行捕获组展开。
14. `{{cwd}}`、`{{home}}` 针对不同 session 动态展开，并正确转义路径中的正则字符。
15. 默认红色和黄色规则包含明确的正向、反向及长输入测试。
16. TUI、RPC、JSON 和 print 模式均能安全加载；无 UI 模式不会等待交互。
17. 受影响 workspace 的 `npm run check` 和 `npm test` 通过。
18. 使用本机最新版 Pi 完成一次不访问真实用户配置的无副作用加载 smoke test。

## 17. v1 明确不做

- allowlist 或独立绿色规则文件。
- 项目级规则。
- 自动合并新版默认规则。
- watcher 或配置热更新。
- 自定义 reload/status slash command。
- 自动执行安全替代命令。
- `suggestedCommand` 模板或正则捕获组替换。
- system prompt 注入。
- 独立审计日志。
- 红色重试阈值或自动 abort Agent。
- OS 沙箱和 Windows 危险命令完整覆盖。
